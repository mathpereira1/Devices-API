# Devices API

A REST API to create, update, query and delete devices, built with .NET 9, ASP.NET Core and PostgreSQL.

## Tech stack

- C# 13 / .NET 9, ASP.NET Core
- PostgreSQL 17 + Entity Framework Core 9
- Scalar Docs
- xUnit, WebApplicationFactory and Testcontainers
- Docker

## Running with Docker

Requirements: Docker.

```bash
docker compose up --build
```

The API is available at `http://localhost:8080`.

The docs are only enabled in the `Development` environment. To see them, start the containers with:

```bash
# bash
ASPNETCORE_ENVIRONMENT=Development docker compose up --build
```

```powershell
# PowerShell
$env:ASPNETCORE_ENVIRONMENT="Development"; docker compose up --build
```

Then open `http://localhost:8080/scalar/v1`.

### Configuration

Every variable has a default, so no setup is needed. To change them, copy `.env.example` to `.env` and set your own.

| Variable                                              | Default      | Description                                 |
| ----------------------------------------------------- | ------------ | ------------------------------------------- |
| `ASPNETCORE_ENVIRONMENT`                              | `Production` | Set to `Development` to enable the API docs |
| `API_PORT`                                            | `8080`       | Host port the API is published on           |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | `devices`    | Database credentials                        |

Database migrations are applied automatically when the API starts.

## Endpoints

| Method   | Route                        | Description                                             | Success                 |
| -------- | ---------------------------- | ------------------------------------------------------- | ----------------------- |
| `POST`   | `/api/devices`               | Create a device                                         | 201 + `Location` header |
| `GET`    | `/api/devices/{id}`          | Get a device                                            | 200                     |
| `GET`    | `/api/devices?brand=&state=` | List devices, optionally filtered by brand and/or state | 200                     |
| `PUT`    | `/api/devices/{id}`          | Fully update a device                                   | 200                     |
| `PATCH`  | `/api/devices/{id}`          | Partially update a device                               | 200                     |
| `DELETE` | `/api/devices/{id}`          | Delete a device                                         | 204                     |
| `GET`    | `/health`                    | Health check (includes the database)                    | 200                     |

Device states: `Available`, `InUse`, `Inactive`.

Example:

```bash
curl -X POST http://localhost:8080/api/devices \
  -H "Content-Type: application/json" \
  -d '{"name": "iPhone 15", "brand": "Apple", "state": "Available"}'
```

### Business rules

- `id` and `createdAt` are generated by the server and can never be changed.
- Name and brand cannot be changed while a device is in use. The rule checks the device's current state, so releasing a device and renaming it must be two separate requests.
- Sending the same name and brand for an in-use device (for example, a `PUT` that only changes the state) is allowed, because nothing is actually changing.
- Devices in use cannot be deleted.
- If `state` is omitted on creation, the device is created as `Available`.

### Errors

| Status | When                                                          |
| ------ | ------------------------------------------------------------- |
| 400    | Invalid input (for example: empty name or brand)              |
| 404    | Device not found                                              |
| 409    | The operation conflicts with the device state (device in use) |
| 500    | Unexpected error (details are logged, not returned)           |

## Architecture

The solution follows Clean Architecture. Dependencies point inward, and the domain depends on nothing.

```
src/
  Devices.Domain          Device entity, business rules, domain exceptions
  Devices.Application     DTOs, repository interface, DeviceService
  Devices.Infrastructure  DbContext, entity configuration, repository, migrations
  Devices.Api             Controllers, global exception handler, composition root
tests/
  Devices.Tests             Domain unit tests
  Devices.IntegrationTests  API integration tests
```

## Design decisions

- Rich domain model: Device protects its own rules (private setters, validation before any change).
- Ids as Guid v7: generated in the domain: avoid colision and, being time-ordered, avoid index fragmentation.
- Dates: only in UTC, following servers stardard.
- Exceptions and global handler: instead of a Result pattern. Domain exceptions map to 400/409 in one place. A Result pattern would make failures explicit in method signatures, at the cost of more code in every layer, by now I prefer keeping simplificated.
- DTOs: for avoiding exposing the entity.
- PUT and PATCH have separate request models: PUT requires every field, PATCH only changes the fields sent.
- Repository pattern: The interface lives in Application and the implementation in Infrastructure, so the application layer does not depend on EF Core.
- Containers: Multi-stage Dockerfile, the API runs as a non-root user, and Compose waits for the database health check before starting the API.

## Future improvements

- Soft delete (`IsDeleted`/`DeletedAt` + a global query filter) to keep an audit trail of deleted devices.
- Pagination for the list endpoint.
- Case-insensitive brand filter.
- Load secrets from a secret manager instead of default credentials, example AWS SSM.
